Plant Inventory, Lots-First

A consumable-inventory tool for a manufacturing plant: track which lots of each SKU are on hand, where they sit, and when they expire — and issue the soonest-expiring lot first (FEFO). Built, shipped, and documented in one pass.

01

What it is, and why it's interesting

Most inventory UIs treat a line as one product. A plant doesn't work that way: the same SKU arrives in batches with different bins, manufacturing dates and expiry dates. The interesting problems are the little ones — dedup, FEFO, expiry state — done right across every surface.

The problem
Lots, not rows. Same SKU, many expiries. Stock runs out, or quietly goes bad.
→
The model
SKU is the catalog; the lot is the row. Non-unique SKU on purpose.
→
The payoff
Catch duplicates, see what's expiring, and always know which lot to issue first.

The decisions that make it what it is

  1. School, not rows — SKU is non-unique.One SKU carries many lots (bins × expiry). The lot is the row; dedup keys on six fields, not the SKU.
  2. Expired ≠ Expiring soon.One server-side day boundary (date('now')) means every card, filter and row agrees: past = Expired, next 30d = Expiring soon.
  3. Import is parsed in the browser; the endpoint stays thin.SheetJS runs locally; the API gets plain rows and does one atomic batch — duplicates skipped, never overwritten.
  4. Dual-layer dedup.The UI pre-warns; the server still returns 409. “Add anyway” is a deliberate override, so the guard can't be bypassed.
  5. UUID keys, generated on the server.D1 UUID tables have no auto-increment; we mint the ID on INSERT instead of reading a rowId that isn't there.
  6. Images behind a proxy, bucket kept private.The browser never holds object-storage credentials.
  7. Tailwind v3, not v4 (in this stack).v4's ESM-only PostCSS plugin silently fails to scan source under CJS — pinned v3 for a build that actually emits color.
  8. Two isolated instances: production + public demo.Same code, different D1 / Tigris / secrets. The demo can't touch the plant's real data.

The whole system hangs off one idea: a lot is identified by six fields. That single rule drives dedup, bulk-import, and the FEFO view.

Attention-first

Expired and Out of stock are red; Low and Expiring-soon are amber; Adequate is calm green. One glance says what to do.

Warn early, block for real

Re-entering an existing lot flags a live warning with the matching lots; the save is blocked unless you tick “Add anyway.”

Two lenses, one data set

Lot-level table for “what's in the bin”; the By-SKU view for “total on hand + which lot do I issue first (FEFO).”

Import that's safe to re-run

Downloadable template, dry-run preview, and a commit that skips duplicates — so uploading the same file twice won't create double lots.

Your own categories & units

Newly-created categories appear in the filter dropdowns automatically; deletions are blocked while still in use.

Bilingual

Docs ship in English and 中文 so the plant's Chinese-speaking operators have the user guide and glossary in their language.

06

Security posture

The code is public; the plant's data is not. That boundary is the whole design.

  • Two isolated instances. Production and the public demo run the same code against different D1 databases, Tigris buckets and secrets — the demo physically can't read your data.
  • Secrets stay out of git. AUTH_SECRET and Tigris keys live in Cloudflare Pages Secrets; wrangler.toml holds identifiers only. .gitignore guards local secret files.
  • Strong auth. PBKDF2-SHA256 (100k), JWT + revocable refresh tokens, three roles, HIBP breach checks, per-IP rate limiting and lockout.
  • Private object storage. Photos are served through a proxy; the browser never holds Tigris keys.
  • Sample data only, publicly. The demo DB and repo carry a neutral sample set — no real suppliers, prices or PII.

Pre-publish checklist

Because early private commits carried secret values that were later removed, the public repo is published as a clean snapshot (no private history), AUTH_SECRET is rotated, and the legacy Turso token is revoked. Details in Deployment & Ops and Security & Access Policy.
